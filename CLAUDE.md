# CLAUDE.md — проект "Симулятор самолетного БПЛА"

Контекст для Claude Code. Прочитать в начале каждой сессии. Здесь — постоянные
правила проекта; конкретику задачи смотри в `TZ_simulator.md`, физику — в
`Физика_справочник_BeardMcLain.md`.

## Что это за проект

Имитационная модель (симулятор) ЛА самолетного типа для магистерской работы
"Разработка зонда измерения аэродинамических характеристик БПЛА". Симулятор —
инструмент главы 8: должен дать графики и числа, доказывающие, что прямое
измерение угла атаки зондом улучшает работу САУ по сравнению с косвенной оценкой.

Автор — руководитель проекта, специалист по БПЛА и ТАУ, отвечает за технические
решения и проверяет код. Claude Code — исполнитель: пишет и запускает код по ТЗ.
Научные развилки, не описанные в ТЗ, не решать молча — выносить автору.

## Текущая фаза (с 2026-10-06) — ЧИТАТЬ ПЕРВЫМ

- **Диплом защищён/окончен. Всё, что связано с зондом (сравнения «зонд vs
  косвенная оценка», s7–s10, УС по зонду), — НА ПАУЗЕ.** Не развивать без
  явной команды автора.
- Цель фазы — **довести симулятор до нормального инженерного состояния**
  (6DOF-модель, согласованные параметры, трим, САУ, графики, навигация).
- План работ фазы и порядок — `docs/DEV_PLAN.md`, раздел «Дорожная карта».
- Режим работы с автором: делать проверяемыми блоками; после блока —
  остановиться, показать результаты (числа/графики), дождаться «ок», затем
  коммит. Нерешённые развилки — вопросом автору с рекомендацией.

## Архитектурные правила (не нарушать)

1. Физика отделена от численного метода. Вся динамика — в чистой функции
   `derivatives(state, controls, t) -> dstate`, без присваиваний к внешнему
   состоянию. Интеграторы (`step_euler`, `step_rk4`) — отдельно, взаимозаменяемы.
2. Состояние — единый numpy-вектор с именованным доступом к компонентам (без
   "магических индексов"). Не хранить состояние россыпью атрибутов объекта.
3. Параметры ЛА/среды/датчиков — в отдельном конфиге, легко подменяемом. Код не
   содержит "зашитых" чисел физики.
4. Управление заморожено на шаг интегрирования (внутри k1..k4 не пересчитывается)
   — это соответствует дискретной природе САУ.
5. Модульность реализована пакетами: `sim/` (физика) → `control/` (управление) →
   `runner.py` / `flight_logger.py` → `viz/` (отображение) → `scenarios/` (прогоны).
   Каждый слой знает только о нижележащих. `viz/` не импортирует `control/`.
   Боковой канал добавляется расширением вектора состояния, не переписыванием продольного.
6. Визуализация полностью отделена от прогона: сценарий отдаёт `Log` в `viz.*`
   или сохраняет `.flightlog` через `FlightLogger`. Анимацию и графики менять
   только в `viz/`, не трогая сценарии.

## Терминология (глоссарий проекта — единообразно в коде и комментариях)

- САУ — система автоматического управления (НЕ "автопилот").
- ЛА — летательный аппарат.
- УА — угол атаки (alpha). УС — угол скольжения (beta). АУ — аэродинамические
  углы (УА и УС вместе).
- ИНС — инерциальная навигационная система (гироскоп + акселерометр, дают углы
  ориентации).
- СВС — система воздушных сигналов. ПВД — приемник воздушного давления.
- АДХ — аэродинамические характеристики (зависимости Cl, Cd, Cm от АУ).
- Зонд — съемный датчик прямого измерения АУ (центральный объект работы).
- Коэффициенты — ТОЛЬКО английская нотация: Cl (подъемная сила), Cd
  (сопротивление), Cm (момент тангажа).
- Критический УА — граница срыва (падение Cl, рост Cd), задает скорость
  сваливания. Наивыгоднейший УА — режим max Cl/Cd.

## Ключевые требования к содержанию (из ТЗ)

- УА определяется по ВОЗДУШНОЙ скорости (с учетом ветра), не по земной. Это
  принципиально для эффекта зонда.
- Псевдодатчики — с шумом и смещением (иначе зонд не отличить от истины).
- "Мир без зонда": косвенная оценка УА как theta - gamma (тангаж с ИНС, угол
  траектории с GPS). Помечать как моделирование, не эксперимент.
- Парный прогон "с зондом vs без": обе САУ ИДЕНТИЧНЫ во всем (ПИД, сценарий,
  ветер, шум общих датчиков), различие только в источнике УА. Зашить это в код.
- Индикация выхода на закритический УА — обязательна (требование плана работы).

## Правила работы с автором

- НЕ выдумывать числовые результаты, измерения, источники. Нет данных — брать
  значения-аналоги (Aerosonde) и явно помечать "параметры-аналог, заменяются",
  либо спрашивать автора. Места для данных автора в ТЗ помечены `[АВТОР: ...]`.
- Различать "моделирование" и "эксперимент": симулятор дает моделирование.
- Не утверждать ничего о реальном железе автора сверх того, что задано в конфиге
  или сказано явно.
- Перед написанием derivatives — сначала выписать реализуемые уравнения (это
  материал для приложения Б диссертации), затем код.
- Код должен быть понятен автору (он защищает каждую строку). Никакой "магии" —
  при усложнении объяснять или упрощать.
- Оформление под ГОСТ и текст диссертации НЕ делать в Claude Code — это
  отдельная задача в чате проекта.

## Текущий статус реализации

### Реализовано (Этапы 0–2 полностью; Этап 3: LQR, АУА, модель 6DOF, боковая САУ)
- Ядро физики: `sim/` — dynamics, aero (sigmoid CL), integrators (RK4+Euler), wind, state
- **Боковая САУ (Б3, 2026-10-06)**: `LateralController` — ПИ курса χ (GPS) → φ_ref
  (±30°) → ПИ крена − Kd·p → δa; ПИ по β (зонд УС) → δr. Коэффициенты рассчитаны
  по B&M гл. 6 для Va=30 м/с (docs/control.md, раздел 9). Сценарии s12, s13.
  Вывод: на аналоге Aerosonde контур β почти не влияет — ЛА сам координирован.
- **Модель 6DOF (Б1, 2026-10-06)**: состояние `[u, w, q, θ, x, h, v, p, r, φ, ψ, y]`
  (индексы 0..5 прежние), управление `[δe, δt, δa, δr]` (2 элемента → δa=δr=0),
  ветер `(Vwx, Vwh, Vwy)`. Боковые коэффициенты `CY_*`, `Croll_*` (момент крена —
  НЕ Cl!), `Cn_*`, инерция Jx, Jz, Jxz — аналог Aerosonde. Уравнения — docs/physics.md.
  Продольный канал при нулевых боковых состояниях совпадает с прежним до бита.
- Управление: `control/` — PitchController (theta+q cascade), SpeedController (Va ПИД),
  псевдодатчики, `estimate_alpha_indirect()` (ИНС+GPS)
- **Gain scheduling в PitchController** (`gain_scheduling=True` в `PitchControlParams`):
  `delta_e *= clip((Va_ref/Va_meas)², gs_scale_min, gs_scale_max)` — компенсирует
  падение эффективности руля высоты при Va ≠ Va_ref. Va_ref = скорость НАСТРОЙКИ ПИД
  (не полёта!). По умолчанию ВКЛЮЧЁН (`gain_scheduling: bool = True` в коде).
- Инфраструктура: `runner.py`, `flight_logger.py` (.flightlog / npz), `viz/` (plotting,
  animate, viewer)
- Сценарии s1–s13: балансировка, кабрирование, пикирование, срыв с индикацией,
  контроль высоты, контроль Va, сравнение оценок УА, метрика энергии, парный
  прогон, АУА, LQR, координированный разворот, боковой ветер
- **s8_b `scenarios/s8_b_motor_work.py` — физически корректная работа мотора**:
  - Метрика `W = ∫T(t)·Va(t) dt` [Дж] вместо прокси `throttle·Va`
  - T вычисляется из модели: `T = 0.5·ρ·S_prop·C_prop·((k_motor·δt)²−Va²)`
  - `gain_scheduling=True`, `Va_ref=30.0` (точка настройки), ретрим на `VA_REF`

## Известные ограничения (не трогать без согласования)

### Адаптивность PitchController к скорости полёта (gain scheduling)

**Реализовано частично.** `PitchControlParams.gain_scheduling=True` масштабирует
выход q-контура: `delta_e *= clip((Va_ref/Va_meas)², 0.25, 9.0)`.
`Va_ref` = скорость настройки ПИД (= 30 м/с), а не скорость полёта.
Это компенсирует изменение аэродинамической эффективности руля ∝ Va².

**Что не охвачено gain scheduling:**
- theta-контур (внешний): полоса пропускания не масштабируется по Va
- SpeedController: feedforward `thr_trim` не пересчитывается на новой Va_ref
- При сильном отклонении от точки настройки (Va < 20 или Va > 40 м/с)
  нужен полный ретрим (`compute_trim(aircraft, Va_actual)`) + обновлённый thr_trim

**Рабочий диапазон с gain_scheduling=True**: Va = 20–35 м/с (scale = 0.73–2.25).
За пределами этого диапазона качество управления деградирует.

**Для s8_b**: использовать `gain_scheduling=True`, `Va_ref=30.0`, ретримироваться
на целевой VA_REF через `compute_trim(aircraft, VA_REF)`.

**Идея на будущее**: добавить speed-dependent feedforward в SpeedController:
  `thr_ff = f(alpha_measured, Va_measured)` — пересчитывать балансировочную тягу
  через модель тяги из `runner.compute_trim` на каждом шаге.

- Крен и курс (РЕШ-22, 2026-10-08) — каскад по схеме PX4/ArduPilot: p_ref = (φ_ref − φ)/τ_φ

### Открытые дефекты и долги (найдены 2026-10-06, не исправлены — см. дорожную карту)
- `compute_trim` — линейный по CL/Cm (без sigmoid), только горизонтальный полёт без
  крена; боковой трим (δa против момента винта) не считает.
- Срыв в Cm и боковые производные после срыва не моделируются (нет данных).
- Якобиан считается в трёх местах (control/lqr.py, checks/check.py, checks/check_lateral.py).
- `Log.E_kin` считается по скорости без ветра (`total_energy(state, aircraft)` в runner)
  — при ветре это кинетическая энергия по земной, а не воздушной скорости.
- `control/lqr.py` использует scipy (DARE) — исключение из правила «только numpy».
- `viz/` не знает о боковом канале (графиков φ, ψ, β, δa, δr, вида сверху нет).
