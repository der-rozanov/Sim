# Журнал принятых решений

Здесь записаны нетривиальные решения, принятые в ходе разработки.  
Цель: следующий разработчик не переоткрывает их заново.

---

## РЕШ-01: Независимые seed для шума в парном прогоне

**Решение:** `rng_probe` и `rng_noprobe` имеют разные seed.

**Почему не синхронные:** При натурных испытаниях броуновское движение молекул воздуха вокруг датчика зонда и вокруг гироскопа независимо. Синхронизация — математическая условность без физического смысла.

**Как применять:** Всегда создавать два независимых `np.random.default_rng(seed_X)`, никогда не использовать один объект rng для обоих прогонов.

## РЕШ-02: Знак CLde и управляющее соглашение

**Решение:** В модели Aerosonde `CLde = -0.36`, `Cmde = -0.5`.

**Физический смысл:** Положительный `δe` — задняя кромка руля высоты **вниз** (по правилу правой руки вокруг y_b). Это уменьшает кривизну горизонтального оперения → CL хвоста падает → CL самолёта падает → `CLde < 0`.

**Следствие для ПИД:** Команда «нос вверх» = `δe < 0`. ПИД контура тангажа должен иметь **отрицательный** знак коэффициента усиления или инвертированную ошибку.

**Балансировка:** Подтверждена расчётом — `δe_trim ≈ -4.5°` при `α_trim ≈ 2.4°`.

## РЕШ-03: УА по воздушной, не по земной скорости

**Решение:** `air_velocity()` в `state.py` всегда учитывает ветер.

**Почему принципиально:** Это центральный тезис диссертации. Косвенная оценка `α_est = θ - γ_GPS` использует `γ_GPS` из земной скорости. При ветре `γ_GPS ≠ γ_air` → ошибка в α. Прямое измерение зондом этой ошибки не делает.

**Где реализовано:** `state.air_velocity()` (вычисляет из воздушной) vs `state.kinematic_gamma()` (из земной — намеренно для «мира без зонда»).

## РЕШ-04: Управление заморожено внутри RK4

**Решение:** `controls` не пересчитываются при вычислении k1..k4.

**Почему:** Соответствует реальной цифровой САУ с частотой дискретизации 1/dt Гц. Контроллер обновляет команды раз в такт, между тактами команды постоянны. Если пересчитывать управление внутри RK4 — это было бы предположением о «мгновенном» контроллере.

## РЕШ-05: h_dot = u·sin(θ) − w·cos(θ)

**Решение:** Такой знак выбран для оси h (вверх положительно).

**Вывод:** В NED-конвенции: `ḣ = -ṗ_d = -(−u·sin(θ) + w·cos(θ)) = u·sin(θ) − w·cos(θ)`.

**Проверка:**
- θ=0, w=0: `ḣ = 0` (горизонтальный полёт) ✓
- θ=0, w>0: `ḣ = -w < 0` (z_b смотрит вниз, w>0 → снижение) ✓
- θ=5°, α=2°, γ=3°: `ḣ ≈ Va·sin(3°)` ✓

## РЕШ-06: Конвенция знаков ветра

**Решение:** `wind()` возвращает `(Vwx, Vwh)` в **земной** СК:
- `Vwx > 0` = попутный ветер (в направлении полёта)
- `Vwh > 0` = восходящий ветер (термик, вверх)

**Поворот в связанную СК** (в `air_velocity`):
```
u_wind = Vwx·cos(θ) + Vwh·sin(θ)
w_wind = Vwx·sin(θ) − Vwh·cos(θ)
```

**Проверка:** При θ=0, попутный ветер 5 м/с → `ur = u - 5` < u → Va уменьшается. Тест в `check.py` это подтверждает.

## РЕШ-07: Квадратичная модель CD (не линейная)

**Решение:** `CD = CDp + CL_lin² / (π·e·AR)`.

**Почему не линейная:** Линейная CD даёт отрицательные значения при отрицательном α (физически бессмысленно — тяга вместо торможения). Квадратичная симметрична по знаку α.

## РЕШ-08: CL0 = 0.28 (не 0.8 из OCR-справочника)

**Решение:** Используется 0.28.

**Почему:** Справочник — OCR русского перевода, часть значений повреждена. В оригинале Beard & McLain CL0 = 0.28. Значение 0.8 из OCR приводит к `α_trim ≈ -6°` — физически неправдоподобно для нормального самолёта.

**Как проверить:** При CL0=0.28, Va=30: `α_trim ≈ 2.4°` — разумно для крейсерского полёта. Подтверждено в `check.py` (тест «L = mg на балансировочной скорости»).

## РЕШ-10: `animate.py` изолирован от симулятора

**Решение:** `animate.py` импортирует только именованные индексы из `state.py`, ничего больше.

**Почему:** Анимация — инструмент визуализации, не часть симулятора. Должна работать с любым логом, независимо от того, как он получен.

## РЕШ-11: Точные тримовые начальные условия через `trim_state()`

**Решение:** `trim_state()` устанавливает `w = Va·sin(α_trim)`, `θ = α_trim` — точный баланс.

**Почему:** Если стартовать с θ=0, w=0 (как делает `initial_state`), самолёт начинает с α=0 вместо α_trim. Это вызывает переходный процесс (кабрирование, рост высоты), который мешает проверить энергетику и качество интегратора.

## РЕШ-12: Боковой канал — расширение единого вектора состояния

**Решение (автор, 2026-10-06):** вектор состояния расширен до 12 компонент
`[u, w, q, θ, x, h, v, p, r, φ, ψ, y]`; индексы 0..5 не изменены. Управление —
`[δe, δt, δa, δr]`, двухэлементное управление дополняется нулями. Ветер —
`(Vwx, Vwh, Vwy)`: боковая компонента дописана последней по той же причине.

**Почему не отдельный модуль 6DOF:** физика осталась бы в двух местах. При
расширении старые сценарии работают без правок, а вырождение 6DOF в продольную
модель проверяется автоматически.

## РЕШ-17: Навигация по точкам — векторное поле + скругление углов (B&M 10–11)

**Решение (агент, 2026-10-06, на проверку автору):** `control/navigation.py` —
следование по прямой и окружности векторным полем (B&M 10.1–10.2), менеджер
маршрута со скруглением углов дугой (B&M 11.2, алгоритм 6). Навигатор выдаёт только
χ_ref и h_ref — существующие контуры не менялись.
Почему скругление, а не переключение по полуплоскости у точки (B&M 11.1): без него
ЛА проскакивает поворот 90° на ~R_min ≈ 160 м и долго возвращается на линию (С14
первой версии: ~95 м отклонения через 15 с после точки). Цена — ЛА не пролетает
саму точку (срез R·(1/sin(ϱ/2) − 1); для 90° и R = 200 м — 83 м). Если нужен пролёт
точно через точку (фото, сброс) — `R_fillet = 0` или траектории Дубинса (B&M 11.3,
не реализованы).
Вынос точек касания ограничен половиной соседних участков (иначе на остром угле
дуга выносилась на километры). Высота — линейно по участку (не по B&M, где высота
задаётся по линии в 3D, — проще, для П-контура высоты разницы нет).

**Решение (агент по поручению автора, 2026-10-07):** канон оставлен, кроме мест,
где он явно нефизичен (все помечены «ПОПРАВКА» в `sim/config.py`, `sim/aero.py`,

1. **α_stall 27° → 16°.** CL_max 2.42 → 1.41 (α ≈ 13°), Va_stall 11.3 → 14.8 м/с.

4. **Свободное вращение винта**: регулятор оборотов не рекуперирует (i ≥ 0). В каноне

**Реактивный момент винта** (канон, B&M слайд 37) кренит ЛА; спиральная мода
неустойчива (T2 = 10 с) — без элеронов продольные сценарии уходили в спираль за

через обёртку `with_roll_hold(controls_fn, ...)`. Шум её датчиков — свой генератор
(seed 7): последовательности шума продольных датчиков и парные прогоны s9/s10 не
меняются по составу; обе ветви пары получают одинаковую САУ по крену.

## РЕШ-20: FPV-самолёт классической схемы с оценочными производными

**Решение автора (2026-10-07):** поведение Aerosonde (11 кг, нагрузка на крыло
20 кг/м²) не устраивает — нужен манёвренный FPV-самолёт. Из вариантов
(Skywalker X8 — летающее крыло с данными NTNU; Zagi из B&M — с известными
ошибками в коэффициентах; классическая схема с оценочными данными) автор выбрал
**классическую схему (киль, руль направления), данные — оценка**.

Реализация: типовой FPV-высокоплан 1.8 м / 2 кг; производные — по геометрии
учебными формулами (Nelson, Raymer, Roskam), расчёт целиком в
`checks/estimate_fpv_aero.py` (воспроизводим, каждое число прослеживается до
формулы). ВМГ — по реальным данным: мотор AT2814 900KV (паспорт), винт APC 11×7E
(продувка UIUC). Структура модели и поправки РЕШ-19 сохранены. Aerosonde
оставлен пресетом `aerosonde_params()`.

Почему не X8: летающее крыло без руля направления — контур β и сценарии с РН
теряют смысл; классическая схема ближе к исходной архитектуре САУ.
Цена: производные — оценка с погрешностью в десятки процентов, а не измерения.
САУ под новый ЛА перенастраивается отдельным блоком.

## РЕШ-22: Крен и курс — каскад по схеме PX4 / ArduPilot

**Решение (автор, 2026-10-08):** контур крена «ПИД по углу» заменён каскадом
угол → заданная скорость крена → элероны: `p_ref = (φ_ref − φ)/τ_φ` с пределом
p_max, `δa = FF·p_ref + ПИ(p_ref − p)` с масштабом по воздушной скорости; курс —
П-контур `φ_ref = atan(Vg·(Vg·κ + K_χ·e_χ)/g)` без интеграла, κ — кривизна
траектории от навигатора. Классы `RollController`/`RollControlParams` (общие для
`LateralController` и `RollHold`), расчёт — `control/tuning.py`, docs/control.md, разделы 5–6.

Причина: на стенде (Bench3D) — рывок и перерегулирование по крену. Прежний закон
пропускал ступеньку уставки через два П-звена: ступенька курса 10° → φ_ref 27.6° за
шаг → элероны почти в упор (18.7°), p 166°/с через 0.05 с, перерегулирование 38 %;
с kd = 0.2 (выставлено на стенде) доминирующий полюс крена смещался 8.4 → 2.3 рад/с,
разнос с курсом пропадал — 67 % и обратный крен −14°. Это бросок через
пропорциональную часть, не через производную (демпфирование уже было по
измеренной p). Каскад — общепринятая схема (PX4 FW_R_TC/FW_RR_*, ArduPilot
RLL2SRV_TCONST/RLL_RATE_*, INAV PIFF): упреждение делает основную работу,
p_max ограничивает скорость крена. Результат: перерегулирование 0 % на
ступеньках 10–90° при 12–25 м/с и в ветре 5 м/с, δa ≤ 8° на ступеньке 10°.
Цена: скольжение на входе в разворот выросло (s12: 7.2° против 5.4° при kd = 0.2) —
крен стал быстрее; координация разворота (перекрёстная связь δa → δr или
r_ref = g·sin φ/V) — следующий шаг.

## РЕШ-23: Координация разворота — ограничение скорости φ_ref и микс δa → δr

**Решение (агент по запросу автора, 2026-10-08):** в `LateralController` добавлены
ограничитель скорости уставки крена (`phi_ref_rate` = 90°/с, PX4 FW_PN_R_SLEW_MAX)
и подмешивание элеронов в руль направления (`da_dr_mix` = −N_δa/N_δr = −0.654,
ArduPilot KFF_RDDRMIX; расчёт — `control/tuning.py`). docs/control.md 6.3.

Причина: после РЕШ-22 на стенде остался рывок на входе в разворот. Автор
предположил резкую дачу РН; проверка показала, что РН плавный (≤ 4.3°, ≤ 21°/с) и
при δr = 0 рывок тот же — его даёт обратное рыскание элеронов при скачке δa ≈ 15°
(уставка крена прыгала за шаг). Результат (ступенька курса 30°, 16 м/с): рывок
носа против разворота −34 → −5.6°/с, угловое ускорение рыскания 498 → 119°/с²,

## РЕШ-26: САУ одним классом — `control/sau.py`

**Решение (агент по запросу автора, 2026-10-09):** вся САУ собрана в класс `SAU`:
датчики → оценка → наведение → внешний продольный контур → защита по α →
тангаж; курс → крен, β → РН. Каждое звено — отдельный заменяемый объект

пользуются им; регуляторы `control/controllers.py` не менялись.

**Почему так:** САУ была собрана трижды (`FullSAU`, `Game._sau`, `Bench._sau`), и
каждая доработка (TECS, новый тангаж, оценка состояния, режимы взлёта и посадки,
LQR/INDI для сравнения) потребовала бы трёх одинаковых правок. Теперь у каждой
доработки есть своё место: новый объект в звене или подкласс `SAU`.

**Как проверено:** s12–s14 совпали до бита (вывод и .flightlog); логика игры и
стенда — до бита против прежнего кода на 120 с с переключением всех режимов.

**Не сделано (следующие блоки):** сами доработки; сценарии s1–s11 по-прежнему
собирают продольные контуры вручную (они проверяют отдельные контуры, как и
checks/check_sau.py).

**Мелкое изменение поведения игры:** при включении САУ теперь сбрасывается и
интеграл высоты (раньше он оставался с прошлого полёта после R); клавиша H на
маршруте останавливает маршрут и переводит САУ в режим тангажа.

## РЕШ-27: TECS — продольный внешний контур по умолчанию

**Решение (агент по запросу автора, 2026-10-09):** `control/tecs.py` — управление
полной энергией (Lambregts; PX4, ArduPilot): газ ← производная полной энергии Ė, тангаж ←
производная баланса энергии Ḃ (docs/control.md, раздел 4). `SAUParams.lon = "tecs"` по умолчанию
(s12–s14, 3D-тренажёр, стенд); раздельные ПИ (`"split"`) остаются — для сравнения.

**Почему так:** раздельные контуры спорят: тангаж держит высоту ценой скорости
(при торможении 16 → 11 м/с — провал до 8.8 м/с и α 7.7°, при снижении газ в нуле 28 %
времени). TECS распределяет энергию: высота и скорость меняются независимо.

**Выбор по ходу расчёта (на проверку автору):**
- внутренние контуры — чистые И (без П-части PX4): П-часть пропускает шум ПВД через
  V̇ (σ газа 0.049 против 0.019);
- пределы набора и снижения — углом траектории по таблице скоростей, из располагаемого
  производной энергии (0.7 от газа 1 и 0) и предела θ = ±15°, а не постоянные м/с;
- балансировка δt*(V), α*(V) — таблицей по скорости (10…28 м/с), а не одной точкой;
- защита от потери скорости с Va_min = 1.25·Va_stall = 9.4 м/с;
- упреждение ḣ на наклонных участках маршрута — по уклону участка (у навигатора
  добавлен `h_slope`, `NavParams` не менялись).

**Стенд (2026-10-09):** вкладка «Высота и скорость (TECS)» вместо «Тангаж / высота» и
«Скорость» (docs/control.md 4.5). Заодно исправлено: ползунок q_max (5…90 °/с) молча
обрезал расчётное 648 °/с до 90 — на стенде руль высоты упирался в ≈3° при ступеньке
высоты (эффект «застревания в наборе», РЕШ-21); диапазон теперь 5…900 °/с, умолчания
всех ползунков проверены на попадание в диапазон.

**Не сделано:** Ė
по акселерометру; сценарии s5–s10 по-прежнему со своими продольными контурами.

**Стенд, умолчания защиты по α (2026-10-09):** α_выход = α_пред − (α_крит − α_пред) = 5.8°
(`Bench3D.default_aua`). Было 10° — от умолчаний AUAParams под Aerosonde (15/20/10°), для
FPV (9/12.2°) это выше порога предупреждения: автомат возвращался в НОРМ внутри зоны ПРЕД.
Соотношение порогов — как у прежних умолчаний. [на проверку автору]

## РЕШ-28: Приводы рулей — апериодическое звено с ограничением скорости

**Решение (агент по запросу автора, 2026-10-09):** рули отрабатывают команду не

## РЕШ-32: Оценка состояния — инерциальный EKF по схеме PX4 EKF2; только 3D

**Решение (автор, 2026-10-17; реализация — агент):** `control/estimator.py`, `StateEstimator` —
звено `estimator` класса SAU. Фильтр с вектором ошибок (17): ориентация (кватернион; ошибка —
вектор поворота), скорость и положение NED, смещения гироскопа и акселерометра, ветер N/E.
IMU — вход прогноза; коррекция — GPS (скорость, положение), барометр, магнитометр (3 оси),
воздушная скорость, синтетическое β = 0. Задержанный горизонт (0.25 с) с буфером IMU и
повторным прогнозом к текущему времени; отбраковка в σ, защита от блокировки, сброс к GPS
без коррекции. В 3D — по умолчанию (решение автора 2026-10-17: `--sensors real`, `--est ekf`;
`--est none` — сырые измерения, `--sensors truth` — истина). s1–s10 не тронуты.

**Почему так.** Сначала был сделан EKF по B&M гл. 8 (ориентация по акселерометру как
«вертикали» + EKF по GPS + фильтры h и Va). Трезвая проверка (автор попросил) показала, что
он работал на подпорках: R акселерометра завышен в 80 раз, отбраковка χ² против ложного крена
до 40° при скольжении, b_r ненаблюдаем, настройка по одному полёту, согласованность (NEES)
не проверялась. Причина — в постановке: модель «акселерометр = вертикаль» верна только в
координированном полёте. PX4 и ArduPilot используют IMU как вход прогноза — тогда вираж и
скольжение не ошибка модели. Переход на эту схему (решение автора) убрал все подпорки.
Физика симулятора (углы Эйлера, 12 состояний) не затронута: у фильтра своё состояние.

Найдено при настройке (моделирование, check_estimator):
- магнитометр — по трём осям: «курс по магнитометру» через оценённый наклон при наклонении
  поля 73° даёт коррелированную ошибку (NEES ориентации 35 → 1.4);
- защита от блокировки: ошибка больше порога отбраковки иначе не исправляется;
- сброс к GPS — только без коррекции (как EKF2_NOAID_TOUT): иначе выброс GPS на 50 м через
  5 с принимался за истину;
- в проверках акселерометр должен считать удельную силу по положениям рулей после привода,
  а не по командам САУ (ошибка была и в проверках 5.2–5.3 B&M-варианта).

Сопутствующие изменения: магнитометр в `RealisticSensors` (поле Земли для Иннополиса,
[АНАЛОГ]); сырые составляющие GPS-скорости; отметки времени отсчётов; `SAU.observe()` —
датчики и оценка без управления (3D вызывает его в ручном полёте); старт в 3D — в
балансировке относительно воздуха (без скачка скольжения при ветре; касается и «истины»).

**Результат:** СКО ошибки φ, θ 0.08°, ψ 0.29°, h 0.06 м, ḣ 0.02 м/с, χ 0.09°; NEES/размерность
0.5–1.4 по всем группам; САУ на EKF — как на истине (перебег крена 0.4°, рули).

**Не сделано:** состояния магнитного поля и смещений магнитометра (поле в симуляторе известно
точно), оценка ухода GPS (не наблюдаем), комплементарный выходной предиктор PX4 (вместо него
повторный прогноз, +1.8 мс на кадр в 3D — сделан 2026-10-29, см. дополнение ниже), несколько
экземпляров фильтра, EKF в s1–s10.

**Дополнение (2026-10-17): диагностика фильтра.** Чтобы работа EKF была видна в 3D, а не только
в `checks/check_estimator.py`: `StateEstimator.status(t)` — внутреннее состояние (невязки и
√S по группам, отношение к порогу, средний NIS, счётчики, время шага, собственные числа P) —
то, что доступно и в реальном полёте; `EstimatorMonitor` — сверка с истиной на том же
задержанном моменте t_f, что у фильтра (иначе σ и ошибка относятся к разным моментам), NEES
по группам. Показ — вкладка ESTIMATOR окна станции (`viz/station.py`), отчёт 10 Гц. Монитор —
в `control/` (знает `sim/`), окно станции по-прежнему не импортирует ни `sim/`, ни `control/`.
Алгоритм фильтра не менялся (проверки — те же числа).

**Дополнение (2026-10-29): выходной предиктор.** Решение автора — выход на текущем времени по
схеме PX4 (`output_predictor.cpp`) вместо повторного прогноза, в 3D — по умолчанию
(`EstimatorParams.output = "predictor"`; `"replay"` — прежний способ, для сравнения).
Выходное состояние — инерциальное счисление по IMU; после шага фильтра на горизонте t_f —
комплементарная поправка по расхождению с фильтром в момент t_f: ориентация — через
приращение угла, k = 0.5·Δt/(t − t_f); скорость и положение — П + малая И, τ = 0.25 с
(EKF2_TAU_VEL/POS), сдвиг всего буфера; скачки сброса к GPS — в выход сразу. Формулы —
docs/control.md, 9.3.

Замер до реализации показал, что повторный прогноз — ≈ 0.05 мс из ≈ 0.22 мс шага фильтра
(основное — прогноз P 17×17 и коррекции); ускорения предиктор не дал (0.30…0.33 мс в обоих
режимах, в пределах разброса). Автор оставил его ради схемы PX4 и сглаженного выхода;
ускорение фильтра — отдельный пункт (последовательная скалярная коррекция, как в EKF2).
Проверка (`checks/check_estimator.py`, раздел 5, моделирование): СКО против истины — на
1…5 % больше, чем у повторного прогноза (сглаживание); расхождение выходов в среднем 0.03°,
наибольшее 0.48° на входе в разворот; замкнутый контур — перебег крена 0.43° против 0.45°;
выход на скачок фильтра — 95 % за 0.56 с, перерегулирование ≤ 5.4 %; на выставке ошибка
против истины не больше, чем у повторного прогноза. Поправку выхода на время выставки
(без сглаживания) автор счёл ненужной.

## РЕШ-33: Дребезг рулей на EKF — фильтр Va для TECS по схеме PX4, фильтр НЧ β (временно)

**Решение (автор, 2026-10-18; реализация — агент):** (1) TECS получает Va и V̇ от собственного
фильтра воздушной скорости, как `TECSAirspeedFilter` в PX4: показание ПВД (`est["Va_tas"]`, а не
оценка EKF |v − w|) + продольная удельная сила акселерометра, комплементарный фильтр 2-го
порядка, ω_V = 1 рад/с, ζ_V = 0.9 (`TECSParams.spd_w0`, `spd_zeta`; расчёт — `tuning.py`).
Без акселерометра (TruthSensors, NoisySensors — s8–s10) — прежняя схема без изменений.
(2) β зонда перед ПИ скольжения — апериодическое звено τ_β = 0.1 с
(`LateralControlParams.beta_tau`; шаблон в `blocks.py` — звено `Aperiodic`). Это временно:
серийные САУ управляют РН по r и a_y, без датчика β — в DEV_PLAN.

**Почему так.** Автор заметил постоянный дребезг рулей в 3D при штиле. Замер (моделирование:
FPV, 16 м/с, штиль, без турбулентности, RealisticSensors + EKF, 50 с горизонта): сам EKF
гладкий (скачок оценки θ за шаг 0.003°, h — 0.004 м). Подстановка истины по одному каналу
показала источники: δr — на 98 % белый шум зонда β (0.57°), идущий в ПИ напрямую
(δr ≈ Kp·σ_β = 0.29°); δe и δt — на ~90 % Va: оценка EKF |v − w| шумит (СКО 0.12 м/с, скачки
до 0.37 м/с за шаг, подвижный ветер q_wind = 0.5), TECS её дифференцирует → V̇ с СКО 0.71 м/с².
Гироскоп — пренебрежимо. В PX4 TECS не берёт Va из EKF, а V̇ получает от акселерометра.
Первая версия фильтра брала V̇ = производную Va_f — в неё входил член 2ζω·e, и шум ПВД
возвращался (δe улучшился лишь на 25 %); V̇ должно идти от f_x и b, без невязки.

**Результат** (ход руля за 50 с; моделирование, FPV, 16 м/с):

| Режим | | δe, ° | δt | δr, ° |
|---|---|---|---|---|
| горизонт, штиль | было | 107.6 | 9.08 | 1598 |
| | стало | 29.6 | 0.78 | 115 |
| Va 16 → 19 м/с и разворот 90° | было | 82.9 | 9.33 | 1599 |
| | стало | 26.1 | 1.11 | 121 |
| ветер 5 м/с + слабая турбулентность | стало (на истине: 116 / 11.1 / 137) | 73.0 | 2.15 | 177 |

Остаток δe (0.008° за шаг) — шум θ, q оценки EKF, равен случаю «Va — истина». Ступенька
Va 16 → 19 м/с: время до 90 % 5.24 с против 5.15 с САУ на истине, перерегулирование 6.6 % против
5.5 %. Цена фильтра β: |β|max в разворотах s8 2.92° → 3.32°, |δr|max 5.4° → 4.9°; s9 |δr|max
8.6° → 6.2°. Продольные s1–s7 и проверки TECS без акселерометра не изменились.

## РЕШ-34: Карты — только вымышленная местность; процедурные карты 10 × 10 км

**Решение (автор, 2026-10-24; реализация — агент):** карты реальной местности (снимки,
рельеф и контуры конкретного места) удалены из проекта и из истории git (соображения
безопасности); реальную местность в проект не добавлять. Взамен — три процедурные карты
(`viz/maps3d.py`): `valley`, `alps`, `marsh`; карта `default` дополнена (хутора,
мельница, рощи, лесополосы, смешанный лес). Мотивы — у реальных ландшафтов (долина
Дуная, альпийская котловина с озером, пойменные болота), рельеф — из шума.

**Почему так.** Общий класс `ProcMap` повторяет схему `World` (сетка → `surface()`,
РЕШ-25): новая карта — это `relief()`, `colors()` и списки объектов. Рельеф —
аналитическая функция, а не загруженные данные: карта детерминирована, ничего не
скачивается, размер репозитория не растёт. Деревья и дома ставятся по высоте
нарисованной сетки (`ground()`), а не по аналитической: быстрее (интерполяция
вместо шума в 300 тыс. точках) и точно на земле.

**Отступ от воды.** На болоте поверхность лежала в ±0.9 м от уровня воды — на дальних
планах вода и земля мерцали (точность буфера глубины при ближней плоскости 0.3 м —
≈ 0.2 м на 1 км, ≈ 2 м на 3 км). Плавный отступ d + 1.5·th(d / 0.3) оставлял ~300
береговых клеток почти параллельными воде (в полосе перехода к равнине), поэтому
отступ — скачком d ± SHORE (3 м) по узлам и после перехода в равнину: каждая береговая
клетка пересекает воду с перепадом ≥ 6 м. Отодвинуть ближнюю плоскость камеры
(0.3 → 1 м) — альтернатива, но в виде из кабины при посадке станет видно отсечение земли.

## РЕШ-35: Ориентация в состоянии — кватернион вместо углов Эйлера

**Решение (автор, 2026-10-27; реализация — агент):** вектор состояния —
`[u, w, q, x, h, v, p, r, y, e0, e1, e2, e3]` (13 компонент), ориентация — кватернион
(B&M, приложение B). Углы Эйлера — производные величины: `euler(state)`,
`with_euler(state, φ, θ, ψ)`, `log.phi | theta | psi`. Повод — пилотажный комплекс
(DEV_PLAN, «Побочная разработка»): кинематика углов Эйлера вырождается при θ = ±90°
(φ̇, ψ̇ ∝ 1/cos θ), а вертикали с вращением есть в нескольких фигурах.

**Почему не защита у θ = ±90°** (ограничить cos θ снизу + приведение углов): интерфейс
не менялся бы, но на вертикалях с вращением (полубочка на вертикали, поворот на
вертикали) оставалась бы ошибка модели. Кватернион убирает особенность полностью; EKF
(РЕШ-32) уже на кватернионе.

**Норма.** В `derivatives` чистая функция не может нормировать состояние, поэтому к
кинематике добавлено λ·(1 − |e|²)·e (B&M ур. B.3), λ = 10 1/с (`QUAT_NORM_GAIN`); при
|e| = 1 оно равно нулю. Матрица поворота строится по нормированному кватерниону.

**Линеаризация.** Линейные модели записываются в углах Эйлера ([u, w, q, θ], [v, p, r, φ]),
поэтому якобиан — общий модуль `sim/linearize.py`: возмущение угла — `with_euler`,
производная — формулы углов Эйлера (`euler_rates`). На него переведены LQR, `check.py`,
`check_lateral.py`, `docs/figures/model_plots.py` (раньше — три копии кода).

**Проверка.** `check.py`, раздел 7: R(кватернион) = R(φ, θ, ψ) до 4e-16; кинематика
кватерниона ≡ кинематика углов Эйлера вне вертикали; полубочка на вертикали (θ = 90.00°)
против точного решения — до 1.6e-9. Регрессия s1–s10 до/после — в отчёте блока.
`archive/probe/` не переведён (вне регрессии; тег `diploma` — состояние на защите).
