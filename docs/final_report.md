# Итоговый отчёт: рекомендации для следующей версии симулятора

**Дата:** 2026-06-13  
**Контекст:** Симулятор самолётного БПЛА, разработан в рамках ВКР «Разработка зонда
измерения аэродинамических характеристик БПЛА». Архитектура устоялась, проект завершён.
Документ фиксирует выводы для следующего проекта.

## 1. Что сохранить без изменений

Эти решения доказали свою работоспособность и образуют скелет следующей версии.

### 1.1 `derivatives()` — чистая функция

```python
def derivatives(state, controls, t, params, wind_fn) -> dstate: ...
```

Физика не имеет побочных эффектов. Следствие: RK4 и Euler взаимозаменяемы в одну
строку, функцию можно использовать для численной линеаризации (раздел 3.1), для
верификации в unit-тестах без контекста. **Не нарушать этот контракт.**

### 1.2 Именованные индексы вектора состояния

```python
U, W, Q, THETA, X, H = 0, 1, 2, 3, 4, 5
```

Читаются как уравнения из учебника. Магические числа — источник скрытых ошибок при
расширении вектора состояния (боковой канал, координаты и т.п.).

### 1.3 Параметры в `dataclass` без зашитых констант

Все числа физики — в одном файле, помечены источником (`[АВТОР]`, `аналог Aerosonde`).
Код физики не содержит ни одной λ-константы. Новая разработка с нуля: начинать с
`config.py` до написания `derivatives()`.

### 1.4 `rng_common` + `rng_probe` в парном прогоне

Одинаковый seed и одинаковый порядок вызовов `rng_common` в обоих прогонах → одна
реализация шума общих датчиков → честное сравнение. Отдельный `rng_probe` для зонда →
независимость, как в натурном эксперименте. Зафиксировано в `decisions.md`, РЕШ-01.

### 1.5 `Log` dataclass + `run()` возвращает лог

Симуляция и визуализация разделены через `Log`. `viz/` не импортирует `control/`.
Это позволило менять графики, анимацию и метрики без касания физики и управления.

### 1.6 Нелинейный CL через σ(α)

Sigmoid-смешение линейного CL и flat-plate даёт физически правдоподобный срыв
без разрыва в точке α_stall. Критическое поведение воспроизводится корректно.

### 1.7 Аналитический тример `compute_trim()`

Система 2×2 решается `np.linalg.solve`. Не итерационный метод — нет сходимости,
нет численного шума. При смене параметров ЛА пересчитывается мгновенно.

## 2. Известные ошибки — исправить в первую очередь

Эти ошибки существуют в текущей версии. Их влияние задокументировано.

### 2.1 Знак `Vx_earth`: три места, одна ошибка

**Правильная формула** (из матрицы поворота вокруг y_body на угол θ):

```
Vx_earth = u·cos θ + w·sin θ   ← должно быть так
ḣ        = u·sin θ − w·cos θ   ← это ВЕРНО (так и написано)
```

**В коде везде стоит минус:** `u·cos θ − w·sin θ`.

Три места: `dynamics.py` (x_dot), `state.py` (kinematic_gamma), `sensors.py`
(measure_gps_velocity_earth). Исправлять все три одновременно — иначе внутренняя
согласованность нарушится и результаты ухудшатся.

**Последствие ошибки:** занижается `Vx_earth` → `gamma_gps` завышается → `alpha_est`
завышается даже **без ветра**. Это добавляет систематический bias к косвенной оценке УА
поверх ветровой ошибки. На триме (θ≈5°, w≈3 м/с) ошибка ~0.5 м/с (~1.5%), при
маневре (θ=15°, w=8 м/с) — до 4 м/с.

**Правило для следующей версии:** перед написанием первого сценария — unit-тест:
при θ=45°, Va=1, α=0 → Vx = cos(45°)·Va ≈ 0.707, Vh = sin(45°)·Va ≈ 0.707.

### 2.2 CD использует CL_linear, а не CL реальный

```python
# aero.py — текущий код
CL_linear = CL0 + CLa * alpha
CD = CDp + CL_linear**2 / (π·e·AR)
```

После срыва реальный CL (blended через σ) падает, но CD считается по линейному CL,
который продолжает расти. Физически: индуктивное сопротивление должно следовать
реальной подъёмной силе, а не её линейной аппроксимации.

```python
# как должно быть
CL_actual = coef_CL(alpha, q, delta_e, Va, params)  # blended
CD = CDp + CL_actual**2 / (π·e·AR)
```

`CL_actual**2 ≥ 0` всегда, деления на отрицательное нет.

### 2.3 `trim_state()` и `initial_state()` — неявная разница

`trim_state()` создаёт ЛА в балансировке (u, w из Va·cos α, Va·sin α, θ = α_trim).
`initial_state()` — θ=0, w=0, вся скорость в u (α=0, не балансировка).

Оба используются в разных сценариях без явного указания. При использовании
`initial_state()` первые 3–5 с — переходный процесс к триму. Это маскирует реальную
динамику. **Правило:** использовать `trim_state()` по умолчанию; `initial_state()` —
только для тестирования переходных процессов с явным комментарием.

## 3. Физическая модель — что улучшить

### 3.1 Численная линеаризация (приоритет: высокий)

Добавить в `runner.py` или `sim/`:

```python
def linearize(state_trim, controls_trim, aircraft, wind_fn, eps=1e-5):
    """
    Возвращает (A, B) — матрицы системы в точке балансировки.
    Численный якобиан: конечные разности от derivatives().
    """
    ...
```

Это открывает: анализ собственных значений (проверка устойчивости), Боде по каналу
δe → θ, расчёт LQR-коэффициентов — всё на чистом numpy, без scipy. Архитектура
позволяет это сделать без изменения остальных модулей.

### 3.2 Атмосфера с зависимостью от высоты (приоритет: низкий)

При диапазоне высот 50–500 м:

```python
rho = rho0 * np.exp(-h / 8500.0)   # стандартная МСА
```

При рабочих высотах 100–150 м разница от постоянного ρ — ~1.2%. Добавлять только
если диапазон высот расширится за 500 м.

### 3.3 Боковой канал (приоритет: для следующего поколения)

Текущая версия — продольный канал (u, w, q, θ, x, h). Боковой канал (v, p, r, φ, ψ, y)
не реализован, что принципиально для задачи зонда угла скольжения (β). Расширение
вектора состояния до 12 компонент — следующий уровень. Архитектура позволяет:
добавить β в air_velocity(), не трогая продольных уравнений.

## 4. Модель управления — что улучшить

### 4.1 Разделить ответственности PitchController (приоритет: высокий)

Текущий `PitchController.step()` возвращает `[delta_e, throttle]`. Throttle считается
из h_Kp · h_err — но в сценариях с `SpeedController` (s9 и далее) этот throttle
выбрасывается (`ctrl.step(...)[0]`). Мёртвый код выполняется на каждом шаге.

**Рекомендация:** `PitchController.step()` возвращает только `delta_e`. Управление тягой —
исключительно `SpeedController` или отдельный `AltitudeController`. Один объект —
одна ответственность.

### 4.2 Anti-windup с back-calculation (приоритет: средний)

Текущий anti-windup: просто clip интеграла. При насыщении руля (δe = ±25°) интеграл
накапливается на полной скорости, что вызывает задержку после выхода из насыщения.

```python
# В PID.step() после вычисления output:
output_unsat = p_term + i_term + d_term
output_sat   = np.clip(output_unsat, min_val, max_val)
if self.Ki > 0:
    self.integral -= (output_unsat - output_sat) / self.Ki * dt  # back-calculation
return output_sat
```

Требует передачи `min_val, max_val` в `PID.step()` — минимальное изменение API.

### 4.3 Документировать знаковую конвенцию (приоритет: высокий)

```python
delta_e_cmd = -self.pid_q.step(error_q, dt)  # ИНВЕРТИРОВАННЫЙ знак!
```

Комментарий фиксирует факт, но не причину. Причина: `CLde < 0`, `Cmde < 0` — нос
вверх требует `δe < 0`. Это B&M конвенция (trailing edge down = positive δe).
При смене конвенции знак сломается молча.

**Рекомендация:** в начале `controllers.py` — блок документации знаковых соглашений:
какое направление δe считается положительным, следствие для момента тангажа, ссылка
на РЕШ-02 в `decisions.md`.

### 4.4 Gain scheduling для обоих контуров (приоритет: средний)

Текущий gain scheduling масштабирует только выход q-контура (δe_cmd *= (Va_ref/Va)²).
Theta-контур не компенсируется, хотя его эффективная полоса пропускания тоже ∝ Va.
Честный gain scheduling — единый коэффициент `qs = clip((Va_ref/Va)², min, max)`,
применяемый к обоим контурам.

### 4.5 Feedforward для снижения по рампу (приоритет: средний)

В s9 весь контур высоты — P-контроллер: `theta_ref = alpha_src + KH · h_err`.
При постоянном снижении (ḣ_ref = const) это даёт установившуюся ошибку высоты
h_ss = ḣ_ref / (KH · Va_trim) ≈ 14 м при ḣ_ref = 0.83 м/с.

Это было «намеренной демонстрацией» разницы зонд vs. оценка. Но смешение двух
эффектов (рамп-lag + alpha bias) затрудняет интерпретацию J_h. Для чистоты результата:

```python
theta_ff  = np.arcsin(np.clip(h_dot_ref / Va_meas, -0.5, 0.5))   # рамп-feedforward
theta_ref = alpha_src + KH * h_err + theta_ff
```

Тогда `theta_ff` убирает рамп-lag в **обоих** прогонах, и J_h отражает только
погрешность alpha_src.

## 5. Процесс разработки — что делать иначе

### 5.1 Верифицировать матмодель до первого сценария

Ошибка знака `Vx_earth` существовала с первых строк и прошла незамеченной сквозь
9 сценариев. Причина: верификация проводилась через «правдоподобность» графиков,
а не через предельные случаи.

**Правило:** до написания первого сценария — набор unit-тестов для `derivatives()`:
- При θ=0, w=0, Va=30: ẋ ≈ 30, ḣ ≈ 0, q̇ ≈ 0 (балансировка).
- При θ=45°, α=0, Va=1: ẋ = cos(45°)·1, ḣ = sin(45°)·1.
- При нулевой тяге и нулевых рулях: ЛА снижается.
- Ветер попутный → Va уменьшается.

4 теста, 20 строк — исключают целый класс знаковых ошибок.

### 5.2 `if __name__ == '__main__':` обязательно в каждом сценарии

Сценарии выполняются при импорте (`import s9` = 90-секундный прогон). Это исключает
параметрический перезапуск, batch-прогоны, тестирование.

```python
def main():
    ...  # весь код прогона здесь

if __name__ == '__main__':
    main()
```

### 5.3 Пресеты через dict или CLI, не через комментарии

«Раскомментируй нужный блок» — редактирование кода вместо конфигурирования.
Нельзя запустить два пресета без изменений файла. Нельзя использовать в CI.

```python
PRESETS = {
    "headwind":   WindParams(Vw_const=-15.0),
    "windshear":  WindParams(Vw_const=-2.0, dV_shear=-6.0),
    "gust":       WindParams(gust_amp=-7.0, gust_t0=35.0),
    "calm":       WindParams(),
}
PRESET = os.environ.get("S9_PRESET", "headwind")
wind_params = PRESETS[PRESET]
```

### 5.4 Typed-интерфейс между слоями

Словарь `meas = {'q': ..., 'theta': ..., 'h': ..., 'Va': ...}` в `PitchController.step()`
не ловит опечатки в ключах. Один `dataclass Measurements` с полями — IDE ловит ошибки,
autocomplete работает, нет `.get()` с молчаливыми дефолтами.

```python
@dataclass
class Measurements:
    q:     float
    theta: float
    h:     float
    Va:    float
```

### 5.5 `_trim_log()` — не копировать поля вручную

При добавлении нового поля в `Log` нужно обновить два места: конструктор в `run()`
и `_trim_log()`. Забыть второе — молчаливый баг.

```python
# Лучше — через dataclasses.fields:
def truncate(log: Log, i: int) -> Log:
    return Log(**{f.name: getattr(log, f.name)[:i] for f in fields(log)})
```
